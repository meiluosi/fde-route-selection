# 成本与延迟

## 先有预算上限，再估支出
“每处理一单花多少钱 × 日均单量 × 天数”只是支出的一半。先问：这个任务做成之后，每单最多值多少？

- 上游 fde-ramp 的四个数字（耗时、日频次、出错率、单次代价）加上人力单价，给出每单人工成本与改进上限；fde-problem-framing 的 [decision.md](https://github.com/meiluosi/fde-problem-framing) 里有增量年收益公式。本 Skill 不重复推导，只用它给出的预算上限去约束选型。
- 每单价值上限 ≈ 每单人工成本 × 预期节省比例 × 可兑现比例。节省比例若已扣除复核工时，成本侧不要再重复计复核。
- 支出超过这个上限，路线要重新设计，而不是硬上。该数字经常让人重新设计方案，这正是它的用处。

## 支出怎么算
按**单位任务**算，再乘以量。

每单成本 = 调用次数 × (1 + 重试率) × (输入 token × 输入单价 + 输出 token × 输出单价) + 检索/向量库/其他每单成本 + 复核成本。

- 输入和输出分开算；检索增强会撑大输入；多步工作流每一步都是一次调用。
- 天数用客户真实运行天数（工作日或自然日），不默认 250 或 365。
- 要有量级敏感性：调用量涨三倍、十倍时年成本如何变化，这也是重开条件。
- 私有化时单价不是 token 价格：算力折旧、运维人员、利用率都是固定成本，按年摊到单量上。利用率低时每单有效成本可能远高于按调用计费，利用率高时反之，需要算出盈亏平衡的日均量。
- 价格会变；单价必须来自带日期的来源（见 [market-snapshot.md](market-snapshot.md)），不凭记忆。

`scripts/cost_model.py` 做这部分算术；它不验证输入，也不含任何真实价格。

```sh
python3 scripts/cost_model.py --in-tokens 3000 --out-tokens 500 --in-price 2 --out-price 8 \
  --orders-per-day 2000 --days 250 --volume-multipliers 1,3,10
```

## 延迟
- 先分场景：嵌在实时工作流里的功能、近实时、后台批处理，可接受的延迟差别很大。
- 区分首字延迟和总时长；能流式输出时，用户感受到的是首字延迟。
- 看 P95，不只看均值；同一时段并发和限流会放大延迟。
- “五秒”是常见经验阈值，不是事实；用真实用户或业务负责人确认本场景的容忍度，并记录来源。
- 延迟决定能不能用更大的模型、要不要流式、要不要小模型或蒸馏；这些在比选时就要一起测，不事后补测。

## 峰值与限流
日均量不等于峰值。问清峰值时段占比和并发要求，核对服务商的限流或私有化的并发能力；放不下就是硬约束，不是优化项。
