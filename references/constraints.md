# 硬约束：先过滤

硬约束的特征：答案会直接淘汰选项，且发现得越晚，推翻的成本越高。合规与部署在国内常常不是技术选择，而是前提，所以放在第一周问。本文件只列要问的问题，不作法律结论；某条规定是否适用、怎样适用，由客户法务/合规确认并给出依据。

## “部署方式”拆成三个问题
“公有云 API / 专有云 / 私有化”常把三件事混在一起，先分开问：

| 问题 | 选项举例 | 为什么要分开 |
|---|---|---|
| 推理在哪里跑 | 厂商公共服务、厂商专属实例、客户云租户、客户机房 | 决定能用哪些模型（私有部署通常只能用能拿到权重的模型）、算力来源 |
| 数据去哪里 | 是否离开客户网络/境内；是否被服务商留存或用于训练 | 同样是“API”，数据条款不同结论不同 |
| 谁来运维 | 厂商、客户 IT、FDE 团队、第三方 | 决定迭代速度、成本结构和责任边界 |

## 要问的问题类别

| 类别 | 问法示例（不是清单式问卷，按缺口选） | 通常由谁回答 |
|---|---|---|
| 数据分类 | 这个场景涉及的数据里，哪些字段/文件不允许离开客户环境？分类分级有没有文件？ | 客户数据负责人、安全 |
| 数据出境与留存 | 数据能否出境？服务商是否留存提示词和输出、留存多久、是否用于训练？ | 法务、安全 |
| 行业与内部制度 | 所在行业的监管、客户内部的采购/安全制度对外部模型服务有什么要求？ | 合规、法务 |
| 服务商资质与备案 | 客户是否要求服务商具备某类资质或备案？备案要求是否适用于这个内部/对外场景？ | 法务（须给依据） |
| 内容安全与审计 | 输出是否需要内容安全审查、留痕、可追溯、可解释？ | 合规、业务 |
| 国产化与采购 | 是否有国产化/信创或采购名录要求？ | 采购、IT |
| 算力与运维 | 若私有化：硬件从哪来，谁能运维，更新模型的流程？ | IT、基础设施 |
| 数据可用性 | 有没有可用的真实样本、标注、知识库？能否脱敏后用于评测？ | 业务、数据负责人 |

## 记录方式
每条约束：ID、约束内容、客户原话、答案、状态、淘汰了什么选项、责任方、来源。

状态只用这几种：**客户确认**（有人明确答复，记录人和日期）、**文件依据**（有制度/合同/文件可定位）、**待确认**（尚未得到答复）、**冲突**（不同人答复不一致）。没有答复就是待确认，不写“应该可以用公有云”。

## 门槛如何影响结论
- 硬约束全部清楚后才能进入模型比选的正式比较。
- 有未清约束时，结论上限为 Investigate，并写明哪些选项暂时不可淘汰。
- 例外：范围明确限定在不触及该约束的原型，如经客户同意的脱敏/合成数据离线基线；结论写“限定范围的 Proceed”并写明不能外推。
- 客户的“要私有化”若来自个人偏好而非制度，写成“待确认来源”，不要当不可协商的约束，也不要当可随意放弃的偏好。

## 私有化的后果要提前写出来
私有化会收窄候选模型池，基线能力可能更低，因此路线判断要在这个更窄的池里重做（见 [routes.md](routes.md)）；成本也从按调用计费变成按算力与运维摊销（见 [cost-latency.md](cost-latency.md)）。这些后果在约束摸底阶段就应告知客户。
